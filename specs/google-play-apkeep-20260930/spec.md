# Google Play: свежий apkeep, приоритет x86_64 и проверка результата

Задача: [STG-5356](https://tracker.yandex.ru/STG-5356).

## Проблема

mdast-cli 2026.9.2 использует внешний или старый встроенный apkeep без проверки версии. Системный apkeep 0.18.0 создаёт пустой каталог, который CLI упаковывает и ошибочно считает успешной загрузкой. apkeep 1.0.0 от 29.04.2026 исправляет авторизацию Google Play; контроль с теми же credentials скачивает настоящее приложение, но выбирает ARM.

## Требования пользователя

- Обновить apkeep до 1.0.0 и перенести настройку выдачи Android x86_64.
- Первый профиль телефона объявляет только x86_64 и использует идентичность upstream x86_64-устройства: Google игнорирует смену ABI при сохранении идентичности Pixel. Проверяется фактическая выдача; при отказе выдачи для этого профиля допускается один запрос штатным ARM-профилем. ARM fallback всегда явно отмечается (подтверждено 30.09.2026). Ошибки входа, сети и повреждённые файлы не являются основанием для fallback.
- Проверять фактическую ABI внутри APK; APK без native libraries принимать как независимый от ABI.
- Пустой или повреждённый результат не считать успешным, возвращать DOWNLOAD_FAILED.
- Выпустить свежую CLI, затем доставить её в dev монолита и Markea через штатный процесс.
- Скачать запрошенные пользователем приложения. Ошибка App Store при авторизации остаётся отдельным внешним блокером, App Store-код не входит в исправление Google Play.

## Границы

Без изменений prod, сетей, авторизации стендов, CI variables и хранилищ. Обновления dev через MR и человеческий аппрув по правилам проекта. Не менять установленные системные инструменты. Не сохранять credentials или одноразовые коды в репозитории, тестах и общих заметках.

## План

1. Зафиксировать upstream apkeep/gpapi и воспроизводимый патч либо профиль x86_64; сохранить upstream license и сведения о сборке.
2. Собрать требуемые host-бинарники, обеспечить их использование установленным wheel и контейнером без зависимости от старого apkeep из PATH.
3. Добавить проверку результата и ABI, явную диагностику ARM fallback; не скрывать ошибки авторизации/сети под fallback.
4. Добавить регрессионные тесты на пустой ZIP, повреждённый APK, x86_64, ABI-independent APK и ARM fallback.
5. Проверить настоящее скачивание с выданным Google-аккаунтом, wheel/sdist и host-бинарники. Выпустить новую версию CLI.
6. Обновить потребителей монолита и Markea, подготовить MR, дождаться человеческого аппрува и штатной доставки dev.
7. Проверить версии и загрузки на обоих dev; при выполнении сканов соблюдать проектный порядок 5-10 приложений с одним начальным контролем.

## Критерии приёмки

- Новая CLI с чистой установкой использует проверенный apkeep 1.0.0 с политикой x86_64 и явно отмеченным ARM fallback.
- Реальная загрузка содержит APK, CRC и AndroidManifest корректны; фактическая ABI записана в диагностике.
- Старый apkeep и пустая выдача больше не приводят к ложному успеху.
- Регрессионные и обязательные проверки CI успешны; опубликованный пакет проверен обратным скачиванием.
- На dev монолита и Markea подтверждены новая версия и результат загрузки через штатный путь.

## Дополнение 01.10.2026: необязательный proxy и восстановление повторных попыток

Проблема: существующий `--google_play_proxy` игнорируется, сборки apkeep не включают SOCKS в reqwest. После сетевого отказа внутренняя повторная попытка apkeep использует уже занятый каталог и возвращает DirectoryExists.

Согласованное поведение:
- Параметр `--google_play_proxy` и Python API `proxy=None` остаются необязательными. Без параметра Google Play использует прямое соединение, независимо от proxy-переменных окружения.
- Явный HTTP/HTTPS/SOCKS5/SOCKS5H proxy применяется к OAuth2 -> AAS и всем запросам загрузки, включая CDN. Адреса и credentials не зашиваются в код. Окружение родительского процесса не меняется.
- Отказ proxy не вызывает перехода на прямое соединение или ARM. В ошибках и логах скрываются credentials и proxy URL; некорректный URL отклоняется до запуска загрузчика.
- Сетевые повторные попытки ограничены тремя запусками в рамках общего timeout, каждый использует собственный временный каталог. Ошибки входа, занятые пользовательские файлы и повреждённые APK не повторяются автоматически.
- x86_64 и явно отмеченный ARM fallback сохраняют прежнюю политику.

План: добавить SOCKS в воспроизводимую сборку всех четырёх бинарников; перенести повторные попытки из apkeep в Python с изоляцией каталогов; передать proxy из обоих публичных путей; обновить документацию, тесты и версию CLI; собрать wheel/sdist и проверить содержимое.

Приёмка: тесты прямого/явного proxy, OAuth и загрузки, приоритета над окружением, закрытого proxy без прямого fallback, отсутствия утечек, повторной попытки после частичного файла, сохранения старых файлов, общего deadline и ARM; фактический SOCKS handshake встроенного бинарника; реальные загрузки разных приложений на dev. Затем PR, проверки, merge, выпуск CLI, доставка через dev и отдельный hotfix prod. Изменения адреса proxy в настройках выполняются DevOps через согласованный MR (STGDEVOPS-1196), не в коде CLI.

## Исправление TLS macOS, 01.10.2026

Пользователь потребовал исправить реальную загрузку macOS и приостановить дальнейшую публикацию/доставку до успешной проверки. Минимальный тест тем же reqwest 0.13.3 воспроизводит `errSSLBadCert (-9808)` с native-tls на двух HTTPS-серверах Google; rustls с включённой проверкой сертификатов возвращает ожидаемые HTTP-ответы. Зависимость gpapi включает native-tls глобально и тем самым меняет backend reqwest для API и загрузчика APK.

План: ограничить native-tls-no-alpn целевыми платформами кроме macOS, на macOS использовать штатный rustls reqwest. Сохранить TLS для запросов авторизации, проверку сертификатов и hostname, SOCKS, приоритет x86_64 и явный ARM fallback. Python-зависимости, включая cryptography, не обновлять. Не менять Keychain/корневые сертификаты компьютера. Выпустить новую ревизию apkeep только после проверки.

Приёмка: регрессионные тесты CLI; отрицательный TLS-тест с недоверенным сертификатом; настоящие загрузки пяти разных приложений на macOS (включая крупные) и контроль Linux; SOCKS и прямой режим, проверка CRC/AndroidManifest/ABI; macOS ARM64 и x86_64 бинарники проверены отдельно. HTTP не использовать для передачи credentials, поскольку проверенный HTTPS-backend доступен. До выполнения этих проверок не публиковать новый релиз и не доставлять потребителей.

По диагностике rustls устраняет TLS-отказ, но согласует HTTP/2, после чего Google отклоняет запрос gpapi с PROTOCOL_ERROR. Сохранить HTTP/1.1 для gpapi на macOS, соответствующий прежнему native-tls-no-alpn. APK CDN может использовать штатное согласование rustls.
