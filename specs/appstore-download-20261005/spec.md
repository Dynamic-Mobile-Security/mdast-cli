# STG-5356: восстановить скачивание App Store через mdast_cli

## Проблема и цель

Пользователь попросил восстановить получение IPA именно через обычный интерфейс mdast_cli. Свежая авторизация сейчас завершается до запроса приложения: HTTP 204/404/403 либо redirect без Location. Старые успешные загрузки подтверждены; конкретная внутренняя причина текущих отказов Apple пока не установлена. На локальном ARM64 SAP helper дополнительно падает в Unicorn при запрещённом sandbox-запросе sysctl. Это отдельное ограничение среды проверки.

## Границы

Только App Store-клиент CLI и необходимые воспроизводимые проверки. Google Play, crypto-зависимости, API стендов, общие сессии, БД, инфраструктура и конфигурация prod/dev не меняются. Не отключать проверку TLS, не отправлять credentials на неподтверждённый endpoint, не использовать unsigned auth; ранее присланный одноразовый код допускается только для ограниченного контроля по явному разрешению пользователя. Не публиковать исправление как работающее без фактической IPA.

## План

1. Сравнить подписанный запрос CLI с официальным ipatool, включая идентичность устройства, транспорт, заголовки и тело. Контроли выполнять в изолированном временном каталоге.
2. Проверить ограниченную обработку временных отказов по актуальному upstream: задержки, Retry-After, HTML 403/429, transport failures. Настоящие ошибки credentials и небезопасные redirect не повторять.
   Проверить передачу credentials через CLI: пустой или отсутствующий 2FA не должен превращать непустой пароль в None. Пароль без кода допустим для начала входа и использования сохранённой сессии; если Apple требует код, завершить вход с понятным сообщением.
   Наблюдаемый HTML 301 без Location допускает только ограниченный повтор на том же уже проверенном auth URL. Это не redirect: новый адрес не подставляется. Любой присутствующий некорректный Location отклоняется сразу.
3. Реализовать только подтверждённые изменения; добавить проверки количества повторов, точной подписи, redirect allowlist, остановки при credential errors и защиты секретов.
4. Проверить штатный вход и загрузку через CLI, затем повтор из другого процесса с сохранённой сессией. Не считать диагностическую подмену транспорта или удалённый signer штатной проверкой локальной версии.
5. Прогнать существующие регрессионные проверки, собрать пакет и подготовить PR только с честным результатом приёмки.

## Критерии приёмки

- Из чистой сессии CLI получает валидную IPA исходного запрошенного приложения и нескольких других бесплатных приложений. ZIP CRC, Payload/Info.plist и исполняемый файл проверены.
- Второй процесс использует сохранённую сессию и повторно скачивает IPA без нового auth POST.
- Повторы ограничены; Retry-After соблюдается либо запрос завершается, если ожидание превышает бюджет. Отказы аккаунта не маскируются под временную сетевую ошибку.
- Нет отправки пароля на чужой host, TLS обхода, утечек credentials/подписи и регрессии Google Play.
- Пароль корректно передаётся через обычные аргументы с кодом, без кода и с пустым кодом; старый аргумент password2FA остаётся совместимым.
- Недоступность локального native signer в sandbox отмечается отдельно. Пока настоящий end-to-end результат не подтверждён, публикация и доставка не выполняются.

## Локальное восстановление, 05.10.2026

Пользователь отдельно попросил добиться работающего скачивания локально. Проверить локальный Docker как диагностический контроль штатной Linux CLI и при необходимости штатный native CommerceKit signer macOS. Все credentials идут только в Apple и через stdin локального процесса. Docker не используется для доступа к запрещённым файлам: mounts ограничены копией CLI и отдельным рабочим каталогом внутри разрешённого workspace/tmp. Без привилегированного контейнера, host networking, Docker socket mount и изменений общих стендов. Ограничения sandbox не обходить.

Если native CommerceKit подтвердит исправление, оформить отдельную реализацию signer с прежними проверками endpoint и точной подписью, тестами и совместимостью Linux. Не добавлять неподтверждённый native backend и не считать Docker-проверку подтверждением исправленного native ARM64.

Дополнительный локальный контроль: собрать штатный darwin-amd64 helper с явно заданным временным каталогом runtime cache вместо недоступного Library/Caches. Использовать Rosetta как поддерживаемый способ запуска x86_64 программы, без изменения sysctl, sandbox, runtime dylib и их checksum. Сначала проверить init/sign на публичном синтетическом payload без credentials. После успешного smoke допускается кандидат настройки helper для проверки обычного CLI. Публикация допускается только после успешного end-to-end результата. Исходники upstream остаются pinned; любые изменения выполняются в отдельной копии при воспроизводимой сборке.

Проверенный smoke: darwin-amd64 через Rosetta с временным cache успешно инициализирован и вернул подпись 501 байт за 6,59 секунды. Реализовать явные необязательные настройки `MDAST_SAP_CACHE_DIR` (абсолютный каталог для проверенных runtime assets) и `MDAST_APPSTORE_SAP_ARCH=amd64` (только выбор штатного helper macOS, без изменения ABI приложений). Без настройки сохраняются прежние пути/архитектура. Некорректные значения отклонять до запуска helper. Cross-arch macOS запускается через `arch -x86_64`, автоматического fallback нет. Не менять HOME, security policy, Apple assets, версии crypto и Google Play. Добавить проверки выбора helper и cache, затем собрать helpers с прежним pin, установить кандидат в отдельное local venv и проверить настоящую CLI с credentials пользователя.

05.10.2026 пользователь явно разрешил один контроль новой локальной сессии с прежним кодом, поскольку свежего кода нет. Код не сохранять. Этот контроль не заменяет end-to-end критерии и не разрешает публикацию без IPA.
