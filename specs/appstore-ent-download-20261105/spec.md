# Восстановление загрузки IPA в mdast-cli для релиза Стинга 2026.11

## Проблема

05.11.2026 установленная CLI 2026.10.3 на двух стендах с одинаковой служебной учёткой после успешного входа получает authorized=false и пустой songList от volumeStoreDownloadProduct. Fallback redownload отвечает пустым HTTP 403. Свежая сессия и контрольное приложение не меняют результат. Upstream ipatool добавил ent/download с привязанными к аккаунту и устройству данными kbsync.

## Цель и границы

Получить рабочий устанавливаемый пакет mdast-cli на актуальном main, не потеряв последующие исправления 2026.10.4/2026.10.5. Проверить реальную IPA обычным интерфейсом AppStore.download_app, затем CLI, без runtime monkeypatch. Перенос в Стинг 2026.11 выполняется позже. Сейчас не публиковать пакет, не менять prod/ГИД, Markea, CI/CD, инфраструктуру, credentials и общий кеш Apple. Работа в detached worktree; чужие ветки не меняются.

## Реализация

1. Проверить источник и pin новой upstream реализации SAP/kbsync; дополнить существующий JSON stdin/stdout helper отдельной операцией kbsync. Credentials ему не нужны. Задать границы времени и размеров, валидировать GUID и DSID, не раскрывать payload/подписи при ошибках.
2. После пустого ответа legacy-download добавить предпочтительный путь ent/download в существующую recovery-цепочку только по точному HTTPS endpoint из Apple bag, без redirects. Передать текущую сессию и корректные поля upstream, фиксировать iOS-версию по каталогу. Проверить соответствие app_id, версии и bundle_id, наличие URL и результата. При отказах сохранить этап и HTTP-статус. Не добавлять бесконтрольные повторы или понижение TLS.
3. Успешный legacy-download не меняется. Если bag не объявляет новый маршрут, сохранить существующий redownload/update fallback. Явный отказ нового маршрута не маскировать как успешную старую загрузку. Не считать пустой songList/HTTP200 успехом.
4. Сохранить публичный API клиента, поддерживаемые платформы и существующие download/register flows. Новые native assets загружать только через проверенный upstream с закреплёнными SHA256. Собрать все шесть helper-артефактов воспроизводимо.
5. Добавить регрессионные тесты: правильный запрос, allowlist/redirect/TLS, несоответствие приложения/версии/пакета, пустой или запрещённый ответ, таймаут/ошибка helper, отсутствие нового endpoint и прежний путь. Выполнить существующий набор тестов и проверки wheel/sdist.

## Приёмка

- Кандидат из собранного wheel получает IPA целевого и минимум двух контрольных бесплатных приложений; CRC, Payload/Info.plist и исполняемый файл проверены. Сами бинарники не передаются в LLM.
- Проверены чистая сессия и второй процесс с сохранённой изолированной сессией. Credentials доступны только диагностическому процессу и Apple, не попадают в аргументы процессов, журналы, репозиторий или артефакты.
- Linux amd64 проверяется реальным скачиванием, другие targets как минимум сборкой и упаковкой; непроверенные runtime-платформы явно указаны. Если доступен локальный macOS helper, выполнить smoke и загрузку.
- Runtime prod/ГИД неизменен: кандидат работает из временного каталога без установки поверх штатной CLI. Новые записи загрузок/сканы на стендах не создаются, временные файлы удаляются.
- Итог: проверенный wheel/sdist, точная версия и SHA256, diff/commit, описание причины и границ проверки для последующего включения в 2026.11.

## Этап выпуска, согласован 05.11.2026

После успешной приёмки кандидат выпускается как стабильная CLI 2026.11.1 через PR по задаче STG-5536. Это разрешение заменяет ограничение публикации первоначального этапа. Изменение версии не меняет протокол кандидата. Критерии: зелёный PR CI, merge обычным способом, тег на merge commit, успешная штатная публикация PyPI и Docker Hub, обратная проверка wheel/sdist. Затем подготовить отдельные MR в dev монолита и main Markea с опубликованной зависимостью, без merge и выкладки этих потребителей. CI/CD и инфраструктуру не менять.
