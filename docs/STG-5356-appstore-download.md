# STG-5356: локальное скачивание App Store восстановлено

## Результат

05.10.2026 установленный кандидат CLI скачал три разные валидные IPA обычным entrypoint, без подмены исходников и удалённого signer. Первый процесс выполнил свежую авторизацию (новая сессия) с ранее присланным кодом по явному разрешению пользователя. Следующие процессы использовали сохранённую сессию без auth POST. Независимый вход из другого чистого каталога без 2FA тоже завершился успешно. Значения credentials и OTP в отчёт не включены.

|---|---:|---:|---|---|
| Исходное приложение | 105 082 550 | 11,28 | 302 → 200 | CRC, Payload/Info.plist, executable |
| Контрольное приложение 2 | 160 140 189 | 7,89 | сохранённая сессия, 0 auth POST | CRC, Payload/Info.plist, executable |

Все процессы завершились exit0. Полученные файлы сохранены локально в закрытом рабочем каталоге. 375 тестов и отдельный security gate20 успешны. Wheel/sdist собраны; все шесть SAP helpers сохранены. Между этим wheel и предыдущим локальным кандидатом изменился только sap.py, четыре apkeep binaries и manifest прежние; runtime-зависимости не менялись. Предыдущая проверка Google Play обычным CLI скачала два разных крупных приложения с x86_64, корректными CRC/AndroidManifest и 4/3APK.

## Подтверждённое отличие auth URL

Первый контроль штатного signer с прежним путём `/authenticate` завершился301 без Location,204,404 за34,67с. В issues [598](https://github.com/majd/ipatool/issues/598) и [607](https://github.com/majd/ipatool/issues/607) есть такие же отказы на текущем upstream и сообщения об успехе с [C++ fork Sorvigolova](https://github.com/Sorvigolova/ipatool).

В исходниках fork (commit7fae0e2) адрес authenticateAccount из bag дополняется trailing slash. Upstream [PR603](https://github.com/majd/ipatool/pull/603), смёрженный01.10, разрешает оба известных пути. В нашей CLI валидатор допускал только вариант без slash. Изолированный контроль с единственным изменением пути на `/authenticate/` успешно прошёл302→200 и скачал IPA105 082 553байта за12,72с. Затем этот вариант реализован в обычном пакете и повторно проверен, результаты выше.

Это установленное различие и проверенный рабочий вариант. Из-за непостоянных ответов Apple нельзя объявлять trailing slash единственной внутренней причиной всех прошлых отказов. В comments issue550/598 есть как успехи после смены сети, так и отказы после обновления/смены сети. Неверный пароль либо OTP из старых HTTP-ответов не следовали. В последнем независимом входе код вообще не понадобился.

## Изменения CLI

- После validation адреса из Apple bag используется известный auth path с одним trailing slash. Host и query сохраняются. Валидатор допускает строго оба известных пути; похожие, двойные, чужие и небезопасные адреса отклоняются до отправки credentials. Валидный redirect используется точно по Location, endpoint при отказе не подбирается.
- Исправлена потеря пароля при пустом/отсутствующем `--appstore_2FA`. Пароль без кода допустим для начала входа и сохранённой сессии. Старый `--appstore_password2FA` совместим. При соответствующем account response CLI требует свежий код.
- Подписанные повторы временных ответов ограничены тремя запросами, с паузами10/20с и Retry-After до30с. Account errors и ошибки сертификата не повторяются. Подписываются именно отправляемые байты. Без unsigned auth и без отключения TLS при авторизации.
- Необязательный `MDAST_SAP_CACHE_DIR` выбирает абсолютный доступный cache runtime assets. На Apple Silicon явный `MDAST_APPSTORE_SAP_ARCH=amd64` запускает packaged Intel helper через установленную Rosetta. Default/native selection прежний, автоматического fallback нет. Runtime assets/checksums, HOME и sandbox не меняются.

Продуктовый scope ограничен CLI. БД, конфигурация и общие сессии стендов не менялись. Это локально проверенный кандидат, опубликованная CLI2026.10.2 этих новых изменений ещё не содержит. Release/tag/deploy в этой проверке не выполнялись.
